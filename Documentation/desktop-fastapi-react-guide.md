# Building a Desktop Python App — FastAPI + React (Vite)

A practical guide to building a **desktop application** using a **FastAPI backend**
and a **React frontend**, bundled into a single executable. Covers the architecture,
the new config files you need, and the role of **Vite**.

---

## TL;DR — what each tool does

| Tool | Side | Role |
|------|------|------|
| **React** | Frontend | The UI (components, pages) |
| **Vite** | Frontend | Build tool + dev server for React. Dev: hot-reload + proxy to FastAPI. Prod: compiles React into static `dist/` files |
| **FastAPI** | Backend | The REST API **and** the server that hands the built React files to the window |
| **uvicorn** | Backend | The ASGI server process that actually runs FastAPI (on `127.0.0.1`) |
| **PyWebView / Tauri / Electron** | Desktop shell | Wraps the local FastAPI URL in a native OS window so it behaves like a desktop program |
| **PyInstaller** | Packaging | Bundles Python + the built `dist/` into a single `.exe` |

> **Note on naming:** the tool is **Vite** (pronounced "veet", French for "fast"),
> not "Vito". It is a JavaScript/React tool — it has nothing to do with Python.

## 1. Architecture

```
┌──────────────────────────────────────────────────────────┐
│  🖥️  Desktop App Window (one .exe)                         │
│                                                            │
│   ┌────────────────────────────┐   ┌───────────────────┐  │
│   │ Desktop Shell              │   │ Python process    │  │
│   │ (PyWebView / Tauri / ...)  │   │                   │  │
│   │                            │   │  FastAPI backend  │  │
│   │   React UI                 │   │  (uvicorn on      │  │
│   │   (built by Vite → dist/)  │   │   127.0.0.1:PORT) │  │
│   │          │                 │   │        ▲          │  │
│   │          │ HTTP fetch      │   │        │          │  │
│   │          └── GET/POST /api ─────────────┘          │  │
│   │          ▲                 │   │        │          │  │
│   │          └── serves built React (StaticFiles dist/)│  │
│   └────────────────────────────┘   └────────┬──────────┘  │
└──────────────────────────────────────────────┼───────────┘
                                                │
                              ┌─────────────────┴───────┐
                              │ Local data (SQLite/files)│
                              │ External APIs (optional) │
                              └──────────────────────────┘

DEV MODE ONLY:
  You → Vite dev server :5173 (hot reload) ·· proxy /api → FastAPI :PORT
```

**Key idea:** The UI never talks to a database directly. It calls the FastAPI
`/api/...` endpoints over HTTP on `127.0.0.1`. FastAPI also serves the built
React files, so in production everything is one app on one local port.

## 2. Build & packaging flow

```
frontend/ (React + Vite)                 backend/ (FastAPI)
  src/*.jsx                                main.py (FastAPI app)
     │                                        │
     │  npm run build (Vite)                  │
     ▼                                        │
  dist/  (index.html + JS/CSS) ───────────────┤  FastAPI mounts StaticFiles(dist/)
                                              │
                                              │  PyInstaller bundles python + dist/
                                              ▼
                                   dist/MyApp.exe  (single desktop binary)
```

1. Vite compiles React → `frontend/dist/`
2. FastAPI serves that `dist/` folder (plus the `/api` routes)
3. PyInstaller packages the Python launcher + `dist/` into one `.exe`

## 4. The new config files (vs a plain FastAPI app)

| File | Belongs to | Role |
|------|-----------|------|
| `frontend/package.json` | Vite/React | Lists React deps; defines `npm run dev` / `npm run build` |
| `frontend/vite.config.js` | **Vite** | Dev-server port, the `/api` → FastAPI **proxy** (dev only), and `base`/output settings for the production build |
| `backend/app.spec` | PyInstaller | Tells PyInstaller to bundle Python + the `dist/` folder into one `.exe` |
| `run_desktop.py` | Desktop shell | Starts FastAPI in a thread, opens a native window pointing at `127.0.0.1` |

## 5. The role of Vite (concretely)

### During development — two servers
- Vite dev server on `:5173` with hot-reload (edit a `.jsx`, UI updates instantly)
- FastAPI on `:8000`
- `vite.config.js` sets up a **proxy** so the UI's `/api/...` calls forward to
  FastAPI — avoids CORS issues.

```js
// frontend/vite.config.js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  base: './',                          // relative paths so FastAPI can serve it
  server: {
    proxy: { '/api': 'http://127.0.0.1:8000' }   // dev-only proxy to FastAPI
  },
  build: { outDir: 'dist' }
})
```

### For production — one app
- `npm run build` → Vite compiles React into `frontend/dist/`
- FastAPI serves that folder — a single app, no separate frontend server:

```python
# backend/main.py
from fastapi import FastAPI
from fastapi.staticfiles import StaticFiles

app = FastAPI()

@app.get("/api/hello")
def hello():
    return {"msg": "from FastAPI"}

# Serve the Vite-built React app (mount LAST, after your /api routes)
app.mount("/", StaticFiles(directory="frontend/dist", html=True), name="ui")
```

## 6. What makes it a *desktop* app

FastAPI + React alone is a web app. To make it feel like a desktop program,
wrap it in a native window.

```python
# run_desktop.py  — using PyWebView (lightweight, pure Python)
import threading, uvicorn, webview
from backend.main import app

def run_api():
    uvicorn.run(app, host="127.0.0.1", port=8000, log_level="warning")

threading.Thread(target=run_api, daemon=True).start()
webview.create_window("My Desktop App", "http://127.0.0.1:8000")
webview.start()
```

Then PyInstaller bundles `run_desktop.py` + Python + the `dist/` folder into a
single `MyApp.exe`.

### Choosing the desktop shell

| Shell | Pros | Trade-off |
|-------|------|-----------|
| **PyWebView** | Pure Python, tiny, simplest with FastAPI | Uses the OS webview (Edge/WebKit) |
| **Tauri** | Very small binary, Rust-based, secure | Needs Rust toolchain; less "Python-native" |
| **Electron** | Most mature, full Chromium | Large binary (~100 MB+) |

For a Python-first team, **PyWebView + PyInstaller** is usually the path of least
resistance.

## 8. Mental model summary

- **Vite** builds the React UI → **FastAPI** serves it → a **desktop shell**
  wraps it in a window → **PyInstaller** packages it into one `.exe`.
- In **dev**: two servers (Vite :5173 + FastAPI :8000), connected by a proxy.
- In **prod**: one server (FastAPI) serving both the API and the built UI, inside
  a native window.
- **New config files** beyond a plain FastAPI app: `package.json`,
  `vite.config.js`, `app.spec`, and a `run_desktop.py` launcher.

## 9. Electron explained (the "web app as a desktop app" framework)

**Electron** builds desktop applications using **web technologies** — HTML, CSS,
and JavaScript — so your React UI runs as a desktop program instead of in a
browser tab.

### What it actually is

Electron bundles two heavyweight pieces into your app:

1. **Chromium** — the same browser engine as Google Chrome. Renders your UI
   (your React app) in a window.
2. **Node.js** — a JavaScript runtime giving the app access to the OS (files,
   menus, notifications, system tray) — things a normal browser can't do.

So an Electron app is basically *"a stripped-down Chrome + Node.js, shipped as a
desktop window."* That's why **VS Code, Slack, Discord, WhatsApp Desktop, and
Figma** are built with it — they're web apps wrapped as desktop programs.

### How it fits the FastAPI + React stack

```
Electron window (Chromium)  →  renders your React UI (built by Vite)
        │
        │  fetch /api/...
        ▼
FastAPI backend (Python, uvicorn on 127.0.0.1)
```

Electron fills the **desktop shell** slot — the same role as PyWebView/Tauri.
It draws the window and loads your UI. Your Python/FastAPI backend still runs as
a separate process that Electron talks to over HTTP.

### Electron's own architecture (two process types)

| Process | Runs | Job |
|---------|------|-----|
| **Main process** | Node.js | Creates windows, menus, OS-level stuff. One per app. |
| **Renderer process** | Chromium | Runs your React UI. One per window. Sandboxed like a web page. |
| **Preload script / IPC** | Bridge | Safe channel for the UI to ask the main process to do OS things |

### Electron vs the Python-based shells

| | **Electron** | **PyWebView** | **Tauri** |
|---|---|---|---|
| Shell language | JavaScript/Node | Pure Python | Rust |
| Binary size | **Large (~100–150 MB)** — ships its own Chromium | Tiny (~10 MB) — uses OS webview | Very small (~5–10 MB) |
| Rendering consistency | Identical everywhere (bundled Chromium) | Varies by OS webview | Varies by OS webview |
| Maturity / ecosystem | **Most mature**, huge community | Modest | Growing fast |
| Fit with a Python backend | Extra Node toolchain to manage | Most natural | Rust toolchain needed |
| Memory use | Heavier | Lighter | Lightest |

### Why a team might pick Electron

- **Consistency:** ships its own Chromium, so the UI looks/behaves identically on
  every machine and OS — no "works on my Windows, breaks on their Mac" webview quirks.
- **Maturity:** the biggest ecosystem — auto-update, installers, native menus,
  tray icons, and abundant community answers.
- **Rich native integration:** deep OS features (global shortcuts, notifications,
  file associations) are well-supported.

### The downsides (why some teams avoid it)

- **Big downloads/installs** — every Electron app carries a full browser (~100 MB+).
  Five Electron apps = five copies of Chromium on disk.
- **Higher RAM/CPU** than a native app.
- **Extra toolchain** — you manage Node.js + its build steps *in addition to*
  Python, adding complexity to a Python-first project.
- **Security surface** — main/renderer isolation must be configured carefully.

### Bottom line

All three shells (Electron, PyWebView, Tauri) sit in the **same architectural
slot** — they just wrap your React + FastAPI app in a window differently.

- Choose **Electron** for maximum UI consistency/polish and a mature ecosystem,
  if the team is comfortable with Node tooling and a large binary.
- Choose **PyWebView** for the simplest Python-native path and a small binary.
- Choose **Tauri** for the smallest, fastest binary, if a Rust toolchain is OK.

A team that previously "used Electron for the UI" almost certainly wanted the
*same-Chrome-everywhere* guarantee and mature tooling, accepting the large binary
in exchange.

## 10. Troubleshooting: blank frontend page (backend starts fine)

**Symptom:** The FastAPI backend initializes/connects fine, but the UI window is
**blank**. Especially when running the **packaged desktop app** (works in dev,
blank in the built `.exe`).

> **Context for this setup:** Electron shell, on Windows. Backend = FastAPI.
> Frontend = React built by Vite. The blank page is almost always a **frontend
> loading** problem, NOT a backend problem — the backend running is a red herring.

### STEP 0 — Open DevTools FIRST (most important)

A blank page means the UI failed to load *something*. The console/network tab
tells you exactly what.

**Electron:** in the main process, after creating the window:
```js
win.webContents.openDevTools()      // or press Ctrl+Shift+I in the window
```

Then check two tabs:
- **Console** → red errors. Common ones:
  - `Failed to load resource ... 404`
  - `Unexpected token '<'` (a JS request returned index.html instead of JS)
  - `ERR_CONNECTION_REFUSED` / `ERR_FILE_NOT_FOUND`
- **Network** → are `index.html`, the JS, and CSS returning **200**, or **404**?

That single check narrows it to one cause below.

### The usual causes, in order of likelihood

#### Cause 1 — Absolute asset paths (the #1 cause)
Vite defaults to **absolute** paths (`/assets/index-abc.js`). When the page is
loaded from disk or under a subpath, `/assets/...` resolves wrong → JS never
loads → blank page + 404 in Network.

Fix in `vite.config.js`, then rebuild (`npm run build`):
```js
export default defineConfig({
  base: './',   // relative, not the default '/'
})
```

#### Cause 2 — Electron loads file:// instead of the FastAPI URL
If Electron loads the built file directly:
```js
win.loadFile('frontend/dist/index.html')   // ← problematic
```
then React Router routes break and `fetch('/api/...')` has no origin to hit → the
app errors and renders blank.

Fix — load the FastAPI server URL instead, and let FastAPI serve the static files:
```js
win.loadURL('http://127.0.0.1:8000')        // ← correct
```

#### Cause 3 — FastAPI static mount wrong / mounted before API routes
If `StaticFiles` points at a missing folder, or is mounted before `/api`, requests
fall through → blank/404.

Fix — mount static **last**, with `html=True`:
```python
app.include_router(api_router)                                          # API first
app.mount("/", StaticFiles(directory=DIST_DIR, html=True), name="ui")   # UI last
```

#### Cause 4 — Packager didn't bundle dist/  (⭐ most likely for "only broken in the build")
Works in dev, blank in the packaged app = the build bundled the Python but **not**
the React `dist/`. At runtime the static dir is empty → blank page.

If packaging the Python with **PyInstaller**:
```python
# app.spec
datas=[('frontend/dist', 'frontend/dist')],
```
And resolve the path at runtime (PyInstaller unpacks to a temp dir `sys._MEIPASS`):
```python
import sys, os
def resource_path(rel):
    base = getattr(sys, "_MEIPASS", os.path.abspath("."))
    return os.path.join(base, rel)

DIST_DIR = resource_path("frontend/dist")
app.mount("/", StaticFiles(directory=DIST_DIR, html=True), name="ui")
```

If packaging with **electron-builder**, confirm the React build and/or the Python
binary are included via the `build.files` / `build.extraResources` config in
`package.json`. A missing `extraResources` entry for the backend or the `dist/`
is a classic cause of a blank window in the installed app.

#### Cause 5 — Window opens before FastAPI is ready (timing)
Electron navigates to `127.0.0.1:8000` before uvicorn is accepting connections →
blank / "can't connect" that never retries.

Fix — wait for the port before loading the URL. Example (Node side, polling):
```js
const net = require('net')
function waitForPort(port, host='127.0.0.1', timeout=10000) {
  return new Promise((resolve, reject) => {
    const end = Date.now() + timeout
    ;(function tryOnce() {
      const sock = net.connect(port, host)
      sock.on('connect', () => { sock.destroy(); resolve() })
      sock.on('error', () => {
        sock.destroy()
        if (Date.now() > end) reject(new Error('timeout'))
        else setTimeout(tryOnce, 150)
      })
    })()
  })
}
// await waitForPort(8000) before win.loadURL(...)
```
Or retry `win.loadURL()` in the window's `did-fail-load` event.

#### Cause 6 — Electron spawns the Python backend but it never actually starts
In a packaged Electron app the backend is often a bundled `.exe` launched via
`child_process.spawn`. If the path to that backend binary is wrong in the packaged
app (dev path vs `process.resourcesPath`), the backend silently fails to start, so
nothing serves the UI.
- Log the spawned process's stdout/stderr to a file and check it.
- Use `process.resourcesPath` (not a dev-relative path) to locate the bundled
  backend in the installed app.

### Quick decision path

```
Blank page
  ├─ Open DevTools → Console & Network
  ├─ JS/CSS return 404?             → Cause 1 (base:'./')  or  Cause 4 (dist not bundled)
  ├─ URL bar shows file://?         → Cause 2 (loadURL http://127.0.0.1 instead of loadFile)
  ├─ ERR_CONNECTION_REFUSED?        → Cause 5 (wait for port) or Cause 6 (backend didn't start) or wrong port
  ├─ "Unexpected token '<'"?        → JS request returned index.html (path/mount wrong — Cause 1/3)
  └─ Works in `npm run dev`, blank in the .exe?  → Cause 4 (bundling) or Cause 6 (backend path)
```

### What to check FIRST for THIS setup (Electron / Windows / only broken in build)

Given it works in dev but the packaged app is blank, start here:
1. **Open DevTools in the packaged app** → read the Network tab. Are JS/CSS 404
   (bundling/path issue) or is it ERR_CONNECTION_REFUSED (backend not running)?
2. `vite.config.js` has `base: './'` and you **rebuilt** after changing it.
3. The packager includes the React `dist/` **and** the Python backend:
   - PyInstaller: `datas=[('frontend/dist', 'frontend/dist')]`
   - electron-builder: `build.files` / `build.extraResources` include them
4. Electron uses `loadURL('http://127.0.0.1:PORT')`, not `loadFile(...)`.
5. The backend binary path in the packaged app uses `process.resourcesPath`
   (Cause 6), and you log its stdout/stderr to confirm it actually launched.
6. Electron waits for the port to be open before `loadURL` (Cause 5).

### Minimal logging to add while debugging
- Electron main: log `win.loadURL(...)` target, and listen for
  `did-fail-load` → print `errorCode`, `errorDescription`, `validatedURL`.
- Backend: write startup + "serving dist from <path>" to a log file, and log the
  resolved `DIST_DIR` and whether it exists (`os.path.isdir(DIST_DIR)`).
- Confirm the port: in DevTools Network, the first request's URL + status.
